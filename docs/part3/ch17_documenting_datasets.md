## Data Without Context

A CSV file with columns named `v1` through `v47`, `site`, `yr`, and `flag` is technically shared, but nobody can use it responsibly. What does `flag` mean? Are the values in `v12` in meters or feet? Why are there no rows from 2019? Were these data collected from a random sample, or from volunteers? Was anything removed?

The person who created the dataset knows the answers. Six months later, they may not. Three years later, a researcher on another continent certainly does not. Dataset documentation exists to transfer that knowledge. It is also where some of the most consequential decisions in AI research are recorded, or fail to be recorded: who is represented in the data, how labels were assigned, and what the data should not be used for.

This chapter covers four layers: a README for orientation, a data dictionary for variables, a datasheet for context and appropriate use, and machine-readable metadata for discovery.

## The Dataset README

Every dataset should have a README, in plain text or Markdown, at the top level of its files. It is the first thing users open. A good dataset README includes:

**Title and summary.** What the dataset is, in one or two sentences.

**Citation.** How to cite the dataset (with its DOI) and the associated paper.

**Creators and contact.** Names, ORCIDs, affiliations, and how to report problems.

**License.** Under what terms the data can be reused (Chapter 18).

**File inventory.** Every file, what it contains, its format, and its size. For large collections, describe the folder structure and naming conventions.

**Collection and processing summary.** How, when, and where the data were collected, and what was done to them before release. Point to the code used for processing (Chapter 4).

**Known issues and limitations.** Missing values, known errors, coverage gaps.

**Versions and changes.** A changelog if the dataset has been updated.

**Checksums.** SHA-256 hashes of each file, so users can verify their download (Chapter 20).

Deep Blue Data curators will ask for most of these, and Chapter 25 has a template.

## Codebooks and Data Dictionaries

A **data dictionary** (sometimes called a codebook) describes every variable in a tabular dataset. It is usually a table:

| Variable | Description | Type | Units / values | Missing |
|---|---|---|---|---|
| `site_id` | Unique identifier for monitoring site | string | e.g., `DET-014` | none |
| `year` | Calendar year of observation | integer | 2015–2024 | none |
| `pm25` | Annual mean PM2.5 concentration | float | µg/m³ | `NA` when <75% of days observed |
| `flag` | Data quality flag | categorical | `0` = valid, `1` = estimated, `2` = suspect | none |

Include units, allowed values or ranges, how missing values are coded, and any transformations applied. Save the data dictionary as a CSV alongside the data so it can be read by software, as well as including it in the README.

### Hands-On: Draft a Data Dictionary from the Data

The mechanical parts of a data dictionary (types, ranges, categories, and missing values) can be computed, which saves time and avoids typos. Only the descriptions need a person:

```python
# scripts/draft_data_dictionary.py
import sys
import pandas as pd

def draft_dictionary(df, max_levels=8):
    """Draft a data dictionary from the data. You still write the descriptions."""
    rows = []
    for col in df.columns:
        s = df[col]
        if pd.api.types.is_numeric_dtype(s):
            values = f"{s.min():g} to {s.max():g}"
        else:
            levels = s.dropna().unique()
            values = ", ".join(map(str, sorted(levels)[:max_levels]))
            if len(levels) > max_levels:
                values += f", ... ({len(levels)} distinct)"
        rows.append({"variable": col,
                     "description": "",                       # fill in by hand
                     "type": str(s.dtype),
                     "values": values,
                     "missing": f"{s.isna().sum()} ({s.isna().mean():.0%})"})
    return pd.DataFrame(rows)

if __name__ == "__main__":
    df = pd.read_csv(sys.argv[1])
    dd = draft_dictionary(df)
    dd.to_csv(sys.argv[2], index=False)
    print(dd.to_markdown(index=False))
```


Open the CSV, fill in the description column, and add units and the meaning of codes (for example, what `flag = 2` means). The draft is also a quick data check: a year of 1900, a negative concentration, or an unexpected category is easy to spot in this table. The same CSV can feed the Kaggle metadata generator in Chapter 15 and the validation schema in Chapter 9, so the documentation, the platform metadata, and the tests all describe the data the same way.

For image, audio, and text datasets, the equivalent is a description of the file structure and any accompanying metadata files: what each label means, how annotations are formatted, and what fields appear in the metadata table.

## Datasheets and Data Cards

A README and data dictionary tell users what is in the dataset. A **datasheet** tells them why it exists, how it came to be, and what it is appropriate for. The concept, "Datasheets for Datasets," was proposed by analogy to the datasheets that accompany electronic components {footcite}`gebru2021`. It is organized as a set of questions in seven sections:

**Motivation.** Why was the dataset created? For what task? Who created and funded it?

**Composition.** What do the instances represent (people, images, documents, sensor readings)? How many are there? Is it a sample, and if so, of what population and how was it drawn? Are there labels, and how were they assigned? Is any information missing? Does the dataset contain data that might be considered sensitive or confidential? Does it identify subpopulations, such as by age or gender?

**Collection process.** How was the data acquired: directly observed, reported by subjects, derived from other data, scraped from the web? Over what time frame? Who was involved in collection, and were they compensated? Was ethical review conducted? Were individuals notified and did they consent?

**Preprocessing, cleaning, and labeling.** What was done to the raw data? Is the raw data saved? Is the preprocessing code available?

**Uses.** What has the dataset already been used for? What other tasks could it be used for? Is there anything about the composition or collection that might affect future uses, for example, a risk of unfair treatment of individuals or groups? Are there tasks for which it should not be used?

**Distribution.** How is it distributed, under what license, and are there any restrictions?

**Maintenance.** Who maintains it? How can the owner be contacted? Will it be updated, and how will users be told? Will older versions remain available?

Not every question applies to every dataset, and it is fine to answer "not applicable." The value comes from being prompted to think about each one. For language data, **data statements** {footcite}`bender2018` add questions about the language varieties, speaker demographics, and annotator backgrounds. Hugging Face dataset cards use a similar structure, and Kaggle's metadata fields cover some of the same ground (Chapter 15).

The "Uses" section deserves particular care for AI research. A dataset of residential building images collected for studying housing quality could, in other hands, be used for targeting or surveillance. Stating explicitly what the dataset was and was not designed for does not prevent misuse, but it sets expectations, informs downstream model cards, and gives reviewers and ethics boards something concrete to assess. Where data come from or affect specific communities, record any agreements made with them (see the CARE principles in Chapter 3).

## Machine-Readable Metadata

Human-readable documentation is essential, but search engines and ML tools also need to understand your dataset. Machine-readable metadata describes a dataset in a structured format that software can parse.

**DataCite and schema.org metadata** are generated automatically by most repositories when you fill in the deposit form. They make your dataset appear in Google Dataset Search, DataCite Search, and similar services. Fill in all the optional fields: keywords, related publications, funding, and ORCIDs all improve discoverability.

**Croissant** is a metadata format designed specifically for machine learning datasets, developed by the MLCommons community {footcite}`akhtar2024`. It builds on schema.org and adds descriptions of the dataset's structure (files, record sets, fields and their types) and how to load it, so that ML frameworks can read a Croissant file and load the data without custom code. A **Responsible AI (RAI)** extension adds fields for limitations, biases, sensitive information, intended uses, social impact, whether data are synthetic, and provenance.

You rarely need to write Croissant by hand. Hugging Face, Kaggle, OpenML, and Dataverse generate Croissant metadata automatically for supported datasets. What you need to add is the responsible AI information, which cannot be inferred automatically. The NeurIPS 2026 Evaluations and Datasets track requires dataset submissions to include Croissant files with RAI metadata, and notes that failing to do so may be grounds for rejection. Other venues are likely to follow.

A fragment of a Croissant file looks like this (the `recordSet` describing files and fields is left empty here for brevity):

```json
{
  "@context": {"@vocab": "https://schema.org/", "cr": "http://mlcommons.org/croissant/", "rai": "http://mlcommons.org/croissant/RAI/"},
  "@type": "Dataset",
  "name": "roof-images",
  "license": "https://creativecommons.org/licenses/by/4.0/",
  "rai:dataLimitations": "Images from three Midwestern cities only; winter images underrepresented.",
  "rai:dataBiases": "Neighborhoods with more street-view coverage are overrepresented.",
  "rai:personalSensitiveInformation": "House numbers and license plates blurred; faces removed.",
  "cr:recordSet": []
}
```

The mlcroissant Python library and an online editor can help you validate and extend Croissant files. A useful exercise is to fetch the Croissant file that Hugging Face generates for your dataset, add the RAI fields, and validate the result:

```bash
pip install mlcroissant
# Hugging Face serves auto-generated Croissant metadata for public datasets
curl -L https://huggingface.co/api/datasets/your-lab/roof-images/croissant -o croissant.json
# ...add rai:dataLimitations, rai:dataBiases, and the other RAI fields in an editor...
mlcroissant validate --jsonld croissant.json
```

The validator separates errors, which must be fixed, from recommendations. A typical recommendation for an otherwise valid file is:

```text
Found the following 1 warning(s) during the validation:
  -  [Metadata(air-quality)] Property "http://mlcommons.org/croissant/citeAs" is recommended, but does not exist.
```

Adding a `citeAs` field with your preferred citation resolves it.

The same library can load records directly from a Croissant file, which is a good test that the metadata is complete enough for someone else to use:

```python
import mlcroissant as mlc
ds = mlc.Dataset(jsonld="croissant.json")
for i, record in enumerate(ds.records(record_set=ds.metadata.record_sets[0].uuid)):
    print(record)
    if i == 2:
        break
```

```text
{'default/site_id': b'DET-012', 'default/pm25': 6.5}
{'default/site_id': b'DET-009', 'default/pm25': 12.0}
{'default/site_id': b'DET-008', 'default/pm25': 11.7}
```

If records load, a machine can read your dataset using only its metadata. If loading fails, the error usually points to a missing or mistyped field, file path, or checksum.

## Documenting AI-Labeled or Synthetic Data

AI is increasingly used to create datasets, not just to learn from them. Models are used to label images, classify documents, transcribe audio, extract information from text, or generate entirely synthetic records. These datasets need extra documentation, because the labeling or generating model is part of the data's provenance.

For **AI-labeled data**, document:

- Which model or models produced the labels, with exact versions or revisions (Chapter 7).
- The full prompt or configuration used, if a language or vision-language model was involved.
- How the labels were validated: what fraction were checked by humans, how those were sampled, and the agreement rate between the AI and human labels.
- Which labels were corrected by humans, if any, and whether this is recorded per instance.
- Known failure patterns of the labeling model on this data.

A good practice is to include a per-instance field indicating the label source (for example, `model`, `human`, or `model_verified`) and, where available, a confidence score. This lets users filter to human-verified labels or weight by confidence.

### Hands-On: Report How Well AI Labels Agree with People

If a person checked a sample of the AI-assigned labels, report the agreement in the datasheet. Raw agreement is easy to understand; Cohen's kappa adjusts for agreement expected by chance; and a per-class report shows whether errors concentrate in some categories:

```python
# How well do AI labels agree with human labels on the verified subset?
import pandas as pd
from sklearn.metrics import cohen_kappa_score, classification_report

labels = pd.read_csv("labels.csv")    # columns: image_id, label_model, label_human (blank if unchecked)
checked = labels.dropna(subset=["label_human"])

print(f"{len(checked)} of {len(labels)} model labels were checked by a person "
      f"({len(checked) / len(labels):.0%})")
print(f"raw agreement: {(checked.label_model == checked.label_human).mean():.1%}")
print(f"Cohen's kappa: {cohen_kappa_score(checked.label_human, checked.label_model):.2f}")
print(classification_report(checked.label_human, checked.label_model, zero_division=0))
```

```text
100 of 500 model labels were checked by a person (20%)
raw agreement: 94.0%
Cohen's kappa: 0.90
              precision    recall  f1-score   support

      intact       0.98      0.92      0.95        59
major_damage       0.80      0.94      0.86        17
minor_damage       0.96      1.00      0.98        24

    accuracy                           0.94       100
   macro avg       0.91      0.95      0.93       100
weighted avg       0.95      0.94      0.94       100
```

Overall agreement is high, but the per-class report shows that the model's `major_damage` labels are the least reliable: one in five is wrong (precision 0.80). That is exactly the kind of detail a downstream user needs, and it belongs in the datasheet's "Known issues" section. The checked sample should be drawn at random, or stratified by class, and the datasheet should say how it was drawn.

The Model Zoo's dataset of AI-validated plant observations from social media is an example of this kind of dataset, where a model is part of how each observation came to be included. *[Author note: expand this into a worked example describing how that dataset documents its validation process.]*

For **synthetic data**, document how it was generated, what real data (if any) the generator was trained on, what statistical properties it is intended to preserve, how its fidelity was evaluated, and what privacy protections apply (Chapter 19). Clearly label synthetic data as synthetic, including in the Croissant `rai:dataSynthetic` field if you use it.
