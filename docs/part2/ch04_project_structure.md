## The Folder Called `final_v3_REAL`

Every researcher has seen a project folder like this: `analysis.py`, `analysis_new.py`, `analysis_new_fixed.py`, a `data` folder containing both raw downloads and cleaned files with no indication of which is which, a `model.pt` from some unknown training run, and a notebook called `Untitled7.ipynb` that turns out to contain the only copy of the figure-generating code.

This structure works fine while you are the only person using it and you remember everything. It fails when a collaborator joins, when a reviewer asks how Figure 3 was produced, or when you come back after a semester away. Reproducibility starts here, with a predictable layout and a history of what changed and why. None of the later chapters work well without it.

## A Layout You Can Hand Off

There is no single correct project structure, but good ones share a few rules {footcite}`wilson2017`: raw data is kept separate and never modified, code lives in one place, outputs are generated by code and can be deleted and rebuilt, and a README at the top explains how everything fits together.

Here is a layout that works for most AI research projects:

```text
my-project/
├── README.md            # What this is, how to run it, how to cite it
├── LICENSE
├── CITATION.cff         # Machine-readable citation (Chapter 10)
├── environment.yml      # or pyproject.toml + uv.lock (Chapter 5)
├── .gitignore
├── data/
│   ├── raw/             # Original data. Read-only. Often not in Git.
│   ├── interim/         # Intermediate outputs of cleaning steps
│   └── processed/       # Final analysis-ready data
├── src/                 # Reusable code: functions, model definitions
│   └── my_project/
├── scripts/             # Entry points: prepare_data.py, train.py, evaluate.py
├── notebooks/           # Exploration. Numbered: 01_explore.ipynb
├── configs/             # Hyperparameters and settings (Chapter 8)
├── models/              # Trained weights. Usually not in Git.
├── results/
│   ├── figures/
│   └── tables/
└── tests/               # Checks that code still works (Chapter 9)
```

A few principles behind this layout are worth making explicit.

**Raw data is sacred.** Never edit files in `data/raw`. Every cleaning step should be code that reads from `raw` and writes somewhere else. If someone asks what you did to the data, the answer is in the scripts, not in your memory.

**Everything in `results` should be reproducible from code.** If you delete the `results` folder, you should be able to regenerate every figure and table by running your scripts. If you cannot, something important is undocumented.

**Notebooks are for exploration; scripts are for production.** Notebooks are excellent for trying things out. But code that produces a figure in your paper, or trains a model you will share, belongs in a script or a module where it can be run top to bottom and tested. The next section explains why.

**Secrets never go in the repository.** API keys, passwords, and access tokens belong in environment variables or a `.env` file listed in `.gitignore`. It is easy to commit a key by accident, and removing it from Git history afterward is painful. If you do commit one, revoke it immediately.

**Sensitive data never goes in the repository.** Protected health information, identifiable survey responses, and data under a data use agreement must not be committed, even to a private repository. Chapter 19 covers alternatives.

If you want a starting template, the Cookiecutter Data Science project provides a similar layout that you can generate with a single command.

### Hands-On: Create the Layout

You can create this layout in a few seconds from a terminal. The last line makes the raw data folder read-only, so that a script that accidentally tries to overwrite raw files fails loudly instead of silently changing your data.

```bash
mkdir -p my-project && cd my-project
mkdir -p data/{raw,interim,processed} src/my_project scripts notebooks \
         configs models results/{figures,tables} tests
touch README.md LICENSE CITATION.cff src/my_project/__init__.py
# copy your original files into data/raw, then lock them
chmod -R a-w data/raw
```

On Windows, use PowerShell's `New-Item -ItemType Directory` for each folder, and set the read-only attribute on the raw files through File Explorer's Properties dialog or with `attrib +R`.

Code in `src/` should never refer to absolute paths on your machine. A small helper that locates the project root makes every script work no matter where it is run from, or who runs it:

```python
# src/my_project/paths.py
from pathlib import Path

ROOT = Path(__file__).resolve().parents[2]   # src/my_project/paths.py -> project root
DATA_RAW = ROOT / "data" / "raw"
DATA_PROCESSED = ROOT / "data" / "processed"
RESULTS = ROOT / "results"
```

Then, in any script:

```python
from my_project.paths import DATA_RAW, DATA_PROCESSED
df = pd.read_csv(DATA_RAW / "survey.csv")
df_clean.to_parquet(DATA_PROCESSED / "survey_clean.parquet")
```

Compare this with `pd.read_csv("C:/Users/jane/Desktop/project/survey.csv")`, which works only on one laptop. Hard-coded paths are one of the most common reasons shared code fails on the first try.

## Git for Researchers

Git is a version control system: it records a history of every change to your files, who made it, and why. GitHub and GitLab are websites that host Git repositories and add collaboration features. The University of Michigan provides GitHub access through its enterprise account, and GitHub offers free accounts with extra features for students and educators.

If you have never used Git, free tutorials such as the Software Carpentry Git lesson cover the basics in an afternoon. This section focuses on habits that make Git useful for reproducibility specifically.

**Commit small and often, with messages that explain why.** A commit message is a note to your future self. "Update code" is useless. "Exclude sensors with >20% missing values, per discussion with co-author" is a lab notebook entry. When a reviewer asks why the sample size changed between drafts, you can find the answer with `git log`.

**Use branches for experiments.** If you want to try a different model architecture, create a branch. If it works, merge it. If not, your main branch is untouched and you have a record of what you tried.

**Commit before you run anything that matters.** Before a long training run or before generating figures for a paper, commit your code. Then record the commit hash alongside your results (Chapter 8 shows how to do this automatically). This single habit creates a link between every result and the exact code that produced it.

**Write a useful `.gitignore`.** Exclude large data files, model weights, virtual environment folders, caches, and anything containing credentials. GitHub maintains template `.gitignore` files for Python and R that are a good starting point. Here is one tailored to the layout above:

```text
# .gitignore
# Environments and caches
.venv/
__pycache__/
.ipynb_checkpoints/
.Rproj.user/

# Secrets
.env
*.pem

# Data and models: tracked with DVC or published elsewhere (see below)
data/raw/*
data/interim/*
data/processed/*
models/*
!**/.gitkeep

# Regenerable outputs
results/figures/*.png
runs/
mlruns/
```

The `!**/.gitkeep` line is a common trick: Git does not track empty folders, so you place an empty `.gitkeep` file in each data folder to keep the structure in the repository while ignoring its contents.

### Hands-On: A First Commit You Will Thank Yourself For

```bash
git init
git add .gitignore README.md LICENSE src/ scripts/ configs/ tests/
git commit -m "Project skeleton: layout, license, and path helpers"

# Before an important run, check that nothing is uncommitted
git status --short         # should print nothing
git rev-parse --short HEAD  # the commit ID to record with your results
```

Two Git commands are especially useful when someone asks how a result came about. `git log --follow -p scripts/clean.py` shows every change ever made to the cleaning script, with dates and messages. `git log -S "min_coverage"` finds every commit that added or removed the text `min_coverage`, which is a fast way to find when a threshold or parameter changed.

## Large Files and Model Weights

Git was designed for text files, and it stores every version of every file forever. Committing a 2 GB model checkpoint, then retraining and committing again, quickly makes a repository unusable. GitHub also blocks individual files over 100 MB. You have three main options for large files.

**Git LFS (Large File Storage)** replaces large files in your repository with small pointer files and stores the real content on a separate server. It works well for moderate numbers of files up to a few gigabytes. GitHub includes a small free LFS quota and charges beyond that. LFS is a good fit for things like a small pretrained model or test data that must travel with the code.

**DVC (Data Version Control)** is an open-source tool that tracks versions of large files and stores them in a location you choose: a cloud bucket, a network drive, or U-M storage like Turbo. Your Git repository contains small `.dvc` files that record exactly which version of the data goes with each commit. DVC also supports pipelines (Chapter 9). It is a good fit when you have many large files that change over the course of a project.

**External hosting with a link** is often the best choice for finished artifacts. Upload the trained model to Hugging Face (Chapter 14) or the dataset to Deep Blue Data or Zenodo (Chapter 16), and put the link and a checksum in your README. Anyone who clones the repository can download exactly the right file, and the artifact gets its own DOI and landing page.

A reasonable pattern for most projects is to use DVC or plain storage during active work, and to publish final artifacts externally at the end.

### Hands-On: Git LFS

```bash
git lfs install                       # once per machine
git lfs track "*.safetensors" "tests/data/*.parquet"
git add .gitattributes                # LFS rules live here; commit them
git add models/small_baseline.safetensors
git commit -m "Add small baseline model via LFS"
```

Anyone who clones the repository with Git LFS installed gets the real files automatically.

### Hands-On: DVC with Storage on Turbo or a Cloud Bucket

```bash
pip install dvc                      # add dvc-s3, dvc-gs, etc. for cloud remotes
dvc init                             # creates .dvc/ and commits nothing yet
dvc remote add -d storage /nfs/turbo/my-lab/dvc-store   # or s3://bucket/path
dvc add data/raw/survey.csv          # creates data/raw/survey.csv.dvc
git add data/raw/survey.csv.dvc data/raw/.gitignore .dvc/config
git commit -m "Track raw survey data with DVC"
dvc push                             # uploads the data to the remote
```

The small `survey.csv.dvc` file contains a hash of the data. A collaborator who clones the repository runs `dvc pull` to download exactly that version. If you later fix an error in the data, run `dvc add` again and commit: the Git history now records which data version went with which code version, and `git checkout <old-commit> && dvc checkout` restores both.

## Notebooks in Version Control

Jupyter notebooks are JSON files that contain code, outputs, and execution metadata all mixed together. This causes two problems for version control. First, diffs are nearly unreadable, because every run changes output cells and execution counts. Second, notebooks encourage running cells out of order, so the saved state of a notebook may not correspond to what you get when you run it from the top. The large study of GitHub notebooks mentioned in Chapter 1 found that out-of-order execution and missing dependencies were among the main reasons notebooks failed to reproduce {footcite}`pimentel2019`.

Several tools help. **nbstripout** automatically strips outputs from notebooks when you commit, so diffs show only code changes. **Jupytext** pairs each notebook with a plain `.py` or `.md` file that is easy to diff and review. **Restart and run all** before committing is a simple habit that catches out-of-order problems.

Setting these up takes a minute:

```bash
pip install nbstripout jupytext
nbstripout --install                 # strips outputs from notebooks on every commit
jupytext --set-formats ipynb,py:percent notebooks/01_explore.ipynb   # pair with a .py file
jupytext --sync notebooks/01_explore.ipynb                            # keep them in sync

# Re-run a notebook top to bottom from the command line, in a fresh kernel
jupyter nbconvert --to notebook --execute --inplace notebooks/01_explore.ipynb
```

The last command is the command-line version of "Restart and run all." If it fails, the notebook was depending on hidden state.

### Hands-On: Guardrails with pre-commit

The `pre-commit` tool runs checks automatically every time you commit, and refuses the commit if a check fails. A small configuration catches three of the most common mistakes: committing a huge file, committing a secret, and committing notebook outputs.

```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v5.0.0
    hooks:
      - id: check-added-large-files
        args: ["--maxkb=5000"]       # block files over ~5 MB
      - id: detect-private-key
      - id: end-of-file-fixer
  - repo: https://github.com/kynan/nbstripout
    rev: 0.8.1
    hooks:
      - id: nbstripout
```

```bash
pip install pre-commit
pre-commit install          # activate the hooks for this repository
pre-commit run --all-files  # check everything once
```

The `rev` values pin each hook to a version, for the same reasons you pin packages (Chapter 5). Run `pre-commit autoupdate` occasionally to move to newer versions deliberately.

The longer-term fix is to move stable code out of notebooks. When a notebook cell becomes a function you reuse, move it into `src/` and import it. The notebook then becomes a thin layer that calls tested code, which is much easier to reproduce.

## Tagging a Release

When you submit a paper, create a Git tag that marks the exact version of the code used:

```bash
git tag -a v1.0-paper-submission -m "Code as submitted to Journal X, 2026-09"
git push origin v1.0-paper-submission
```

On GitHub, you can turn a tag into a Release, which gives it a page and downloadable archive. If you connect your repository to Zenodo (Chapter 16), every GitHub Release is automatically archived with its own DOI. Cite that DOI in your paper's code availability statement instead of the bare GitHub URL. If you revise the code during peer review, create a new tag and release. Each will have its own DOI, and your final paper can cite the version that matches the published results.
