## Start Here

[Chapter 22 of the AI in Research Handbook](https://midas-ai-in-research.readthedocs.io/en/main/part2/ch22_reproducibility.html) introduces the three main layers of environment control: virtual environments (`venv`) isolate packages, Conda also manages the Python interpreter and compiled libraries, and Docker controls the operating system. If those terms are unfamiliar, read that chapter first.

This chapter goes one level deeper. Most researchers who have been told to "save your environment" run `pip freeze > requirements.txt` or `conda env export > environment.yml` once and consider the job done. Those files help, but they often do not rebuild the same environment a year later, and sometimes do not rebuild at all on a different computer. The reason is the difference between a specification and a lock.

## Specifications vs. Lockfiles

A **specification** says what you want: "I need pandas, scikit-learn, and PyTorch, with pandas at least version 2." It is written by a human, is short, and deliberately leaves room for flexibility.

A **lockfile** records exactly what you got: every package, including all the packages those packages depend on (the transitive dependencies), with an exact version number and usually a cryptographic hash of the file that was downloaded. It is generated by a tool, is long, and leaves no room for flexibility.

You need both. The specification is what you edit when you add a dependency. The lockfile is what you use to rebuild the environment exactly.

Consider what happens with a specification alone. A `requirements.txt` that lists `torch` and `transformers` without versions will install the latest versions available on the day someone runs it. Next year those will be different, and your code may break or silently produce different results. Pinning top-level packages (`torch==2.4.1`) helps, but their dependencies can still drift. A lockfile captures everything.

What about `pip freeze`? It produces a list of exact versions, which is closer to a lockfile. But it records everything in the environment, including packages you installed for a one-time experiment and then forgot about. It also does not distinguish between packages you chose and those that came along as dependencies, which makes it hard to update later. And it records versions for your operating system only: a frozen list from a Mac may include packages that do not exist on Linux.

Similarly, `conda env export` without flags produces a file full of platform-specific build strings that will often fail on another operating system. `conda env export --from-history` produces a portable specification but not a lock.

The tools below handle both halves properly.

### What the Difference Looks Like

Here is a specification, the part you write by hand in `pyproject.toml`:

```toml
[project]
name = "roof-classifier"
requires-python = ">=3.11,<3.12"
dependencies = [
    "pandas>=2.2",
    "scikit-learn>=1.5",
]
```

And here is a small excerpt of the lockfile that a tool generates from it. Every package, including ones you never asked for, such as `threadpoolctl`, is pinned to one version and one file hash:

```toml
[[package]]
name = "threadpoolctl"
version = "3.5.0"
source = { registry = "https://pypi.org/simple" }
wheels = [
    { url = "https://files.pythonhosted.org/.../threadpoolctl-3.5.0-py3-none-any.whl",
      hash = "sha256:..." },
]
```

You never edit the lockfile by hand. You edit the specification and let the tool regenerate the lock.

## Python Tooling

There are several good tools. The most important choice is to pick one per project and use it consistently.

### uv

`uv` is a fast, modern Python package and project manager that has become widely adopted. It manages the Python version, creates the virtual environment, and maintains both a specification (`pyproject.toml`) and a cross-platform lockfile (`uv.lock`) automatically.

```bash
# Start a new project with a specific Python version
uv init my-project --python 3.11
cd my-project

# Add dependencies (updates pyproject.toml and uv.lock)
uv add "pandas>=2.2" scikit-learn torch

# Anyone else, on any OS, reproduces the exact environment
uv sync --frozen

# Run code inside the environment
uv run python scripts/train.py
```

The `--frozen` flag tells uv to install exactly what is in the lockfile without trying to update anything. Commit both `pyproject.toml` and `uv.lock` to your repository.

A few more uv commands cover most day-to-day needs:

```bash
uv python pin 3.11.9                 # writes .python-version; commit it
uv add --dev pytest nbstripout       # tools for development only, not needed by users
uv lock --upgrade-package pandas     # deliberately update one package, nothing else
git diff uv.lock                     # see exactly what changed before committing

# For collaborators who do not use uv, export a pinned requirements file with hashes
uv export --format requirements-txt --no-dev > requirements.txt
pip install --require-hashes -r requirements.txt
```

The `--require-hashes` flag makes pip refuse to install anything whose file hash does not match the lockfile, which protects against both drift and tampered packages.

### pip-tools

If you prefer to stay close to standard `pip` and `requirements.txt` files, `pip-tools` adds a locking step. You write a short `requirements.in` with the packages you need, and `pip-compile` produces a fully pinned `requirements.txt` with hashes.

```bash
# requirements.in contains: pandas>=2.2, scikit-learn, torch
pip-compile --generate-hashes requirements.in   # writes requirements.txt
pip-sync requirements.txt                        # installs exactly that
```

A `requirements.in` file is short and readable:

```text
# requirements.in: what this project needs, with loose bounds
pandas>=2.2
scikit-learn>=1.5
matplotlib
```

The generated `requirements.txt` lists every package with an exact version, a hash, and a comment explaining why it is there:

```text
joblib==1.4.2 \
    --hash=sha256:...
    # via scikit-learn
pandas==2.2.3 \
    --hash=sha256:...
    # via -r requirements.in
```

The `# via` comments are a useful bonus: when you wonder why a strange package is installed, the lockfile tells you which of your dependencies pulled it in.

The lockfile from pip-tools is specific to the platform and Python version it was generated on, so note both in your README.

### Conda with conda-lock, or pixi

If you need Conda for compiled dependencies such as GDAL for geospatial work, or CUDA libraries, `conda-lock` generates lockfiles from an `environment.yml` for several platforms at once:

```yaml
# environment.yml: the specification
name: geo-model
channels:
  - conda-forge
dependencies:
  - python=3.11
  - gdal=3.9
  - geopandas=1.0
  - pip
  - pip:
      - torchgeo==0.6.1
```

Note the single channel. Mixing `defaults` and `conda-forge` is a common cause of environments that solve differently on different machines. Then generate and use the lock:

```bash
conda-lock -f environment.yml -p linux-64 -p osx-arm64 -p win-64
conda-lock install -n my-env conda-lock.yml
```

`pixi` is a newer tool that brings uv-style project management to the Conda ecosystem, with a `pixi.toml` specification and a `pixi.lock` lockfile. It is a good option for new projects that need Conda packages.

### A Note on GPU Packages

Deep learning frameworks complicate things because the same package (for example, PyTorch) comes in different builds for different CUDA versions and for CPU only. Your lockfile will record the build you installed. If a collaborator has a different GPU or driver, they may need a different build. Document which CUDA version your lockfile targets, and consider providing a CPU-only lockfile or instructions as a fallback. With pip, the PyTorch build is chosen by the package index:

```bash
# CUDA 12.1 build
pip install torch==2.4.1 --index-url https://download.pytorch.org/whl/cu121
# CPU-only build: much smaller, works anywhere
pip install torch==2.4.1 --index-url https://download.pytorch.org/whl/cpu
```

Check the PyTorch website's installation selector for the current index URLs. Containers (Chapter 6) are the most reliable solution for GPU environments.

## R and Mixed-Language Projects

For R projects, `renv` is the standard tool. It creates a project-specific library and a lockfile (`renv.lock`) that records the exact version and source of every package.

```r
renv::init()       # set up renv for this project
# ... install and use packages as usual ...
renv::snapshot()   # record current package versions in renv.lock
renv::restore()    # (collaborator) install exactly what renv.lock says
```

`renv` does not manage the R version itself. The `rig` tool installs and switches between R versions, and you should record the R version in your README. For long-term reproducibility, you can point `renv` at a dated snapshot of CRAN, such as those provided by Posit Public Package Manager, so that packages are installed as they existed on a specific date:

```r
# Install packages as they were on CRAN on 1 September 2026
options(repos = c(CRAN = "https://packagemanager.posit.co/cran/2026-09-01"))
install.packages(c("tidymodels", "ranger"))
renv::snapshot()

# Record the full R environment alongside results
writeLines(capture.output(sessionInfo()), "results/sessionInfo.txt")
```

The dated URL is recorded in `renv.lock`, so `renv::restore()` uses the same snapshot years later. Check Posit Public Package Manager's documentation for the current URL format.

Projects that mix Python and R (for example, using `reticulate`) should lock both sides: `renv.lock` for R and `uv.lock` or `conda-lock.yml` for Python. A container that includes both (Chapter 6) is often the simplest way to guarantee they work together.

## Recording the Invisible Layers

Even a perfect lockfile does not capture everything that can affect your results. The Python version, the operating system, the CPU architecture (Intel vs. Apple Silicon), the GPU model, the NVIDIA driver version, and the CUDA and cuDNN versions all matter for deep learning, and none of them appear in a Python lockfile.

A simple habit is to save an environment report alongside every important result. Here is a short script you can adapt:

```python
# scripts/environment_report.py
import json, platform, sys, subprocess
from importlib.metadata import version, PackageNotFoundError

def pkg(name):
    try:
        return version(name)
    except PackageNotFoundError:
        return None

report = {
    "python": sys.version,
    "platform": platform.platform(),
    "machine": platform.machine(),
    "packages": {p: pkg(p) for p in ["numpy", "pandas", "scikit-learn", "torch", "transformers"]},
}

try:
    import torch
    report["cuda_available"] = torch.cuda.is_available()
    if torch.cuda.is_available():
        report["cuda_version"] = torch.version.cuda
        report["cudnn_version"] = torch.backends.cudnn.version()
        report["gpu"] = torch.cuda.get_device_name(0)
except ImportError:
    pass

try:
    report["git_commit"] = subprocess.check_output(
        ["git", "rev-parse", "HEAD"], text=True).strip()
except Exception:
    report["git_commit"] = None

print(json.dumps(report, indent=2))
```

Run it with `python scripts/environment_report.py > results/environment.json` and commit the output with your results. When a collaborator gets different numbers, comparing environment reports is often the fastest way to find out why. Chapter 8 shows how to capture this automatically with every training run.

### Hands-On: Compare Two Environments

When you and a collaborator get different numbers, run the report on both machines and compare them with a few lines of Python:

```python
# scripts/compare_environments.py
import json, sys

def flatten(d, prefix=""):
    out = {}
    for k, v in d.items():
        key = f"{prefix}{k}"
        if isinstance(v, dict):
            out.update(flatten(v, key + "."))
        else:
            out[key] = v
    return out

a = flatten(json.load(open(sys.argv[1])))
b = flatten(json.load(open(sys.argv[2])))
for key in sorted(set(a) | set(b)):
    if a.get(key) != b.get(key):
        print(f"{key:30} {str(a.get(key)):40} {b.get(key)}")
```

```bash
python scripts/compare_environments.py mine.json theirs.json
```

Example output:

```text
gpu                            NVIDIA A100-SXM4-80GB                    NVIDIA GeForce RTX 3080
packages.scikit-learn          1.5.2                                    1.4.0
python                         3.11.9 (main, ...)                       3.12.4 (main, ...)
```

Here the different scikit-learn and Python versions are the first suspects. The GPU difference may also explain small numerical differences (Chapter 7).

## Updating Without Breaking Things

Lockfiles freeze your environment, but you will still need to update packages occasionally, for security fixes or new features. Do it deliberately: update the lockfile in a separate commit, rerun your tests and a key result, and note in the commit message what changed. If a result changes after an update, you will know exactly which update caused it. Chapter 9 shows how to automate this check.

A safe update routine with uv looks like this:

```bash
git switch -c update-deps
uv lock --upgrade                 # or --upgrade-package <name> for just one
git diff --stat uv.lock           # how much changed?
uv sync --frozen && uv run pytest # do tests still pass?
uv run python scripts/train.py --config configs/smoke.yaml
git commit -am "Update dependencies; tests pass, smoke metrics unchanged"
```

Because the update happens on a branch, you can throw it away if anything breaks.

## Try This

Pick a current project and create a lockfile for it using the tool that fits your stack. Then, on a different machine or in a free cloud environment such as GitHub Codespaces, clone the repository and rebuild the environment using only the lockfile and your README. Run your main script. If it fails, fix the README or the lockfile until it works from scratch.
